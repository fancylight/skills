# 工程质量约束

供 Flow 各阶段按下面的章节使用。规则服务于用户目标，不增加授权、阶段或状态机；用户的明确约束优先。检查结论进入现有设计、审核或测试报告，不另建追踪文档。

## 设计与验证

- 先核对相关入口、公共组件、查询/分页、任务与存储能力，以及目标环境和依赖版本。只调查影响本次决策的范围；记录可定位来源，不把版本未知写成默认兼容。
- 新能力应说明现有实现的具体缺口，以及直接复用、兼容扩展或新建的选择理由。某一个方法不适用，不等于整个组件不能复用；不得用“不改变正式行为”推导“旧代码零修改”。
- 新表、技术标识、状态、锁、后台任务及兼容分支必须对应当前需求或已证实的失败场景。说明生命周期和验证方式；优先使用已有机制，不为假设中的未来预建。必要的版本隔离可以保留，不机械禁止 versionId。
- 影响正确性的环境未知项和无依据的新机制不得通过相关设计结论；说明缺失信息与可继续的工作。没有运行证据时不宣称兼容性或性能已经验证。

## 实现与审核

- 先读适用的项目规范和相邻实现，沿用项目分层、异常、查询、日志及依赖用法。设计假设与代码或环境冲突时明确反馈，不通过另造一套能力掩盖冲突。
- 审核同时检查需求正确性、兼容性、复用、必要复杂度、回归风险和项目编码规范；设计本身存在问题时也须指出。不能仅以“代码与设计一致”判 PASS。
- 格式化、编译、功能测试和规范检查是不同证据。Java 变更执行项目已有检查，并使用独立 NeedBraces 检查作为最低保障；它不代表完整阿里 Java 规范检查。
- 独立检查器为同目录上级的 [scripts/check-java-style.ps1](../scripts/check-java-style.ps1)。传入 RepositoryPath、BaseRevision、Files（本次明确文件清单）、ReportDirectory；不扫描整个业务仓、不改变业务 POM。
- BaseRevision 使用本次实现开始前已确认的提交，随审核请求传递；不得在修改后取 HEAD 来抹去新增违例。报告使用独立缓存/证据目录，禁止覆盖源文件；这一证据不改变审核只读源码的边界。
- 新增违例 FAIL 或必要检查 UNVERIFIED 时，Java 相关审核沿用现有 REJECT，附原因和证据；非 Java 的 NOT_APPLICABLE 不阻塞。不因无关历史违例扩大修改范围，不为取得 PASS 静默忽略解析错误。
- 性能检查只覆盖本次涉及的查询、循环、锁和异步处理成本。存在风险时给出具体证据与验证范围；不强制每个小改动做容量测试。

## 测试与排障

- 验收要求对应真实输入、动作、断言和实际运行环境；区分单元、集成、环境兼容与容量结果，列出关键反例和未覆盖项。
- 使用目标兼容版本验证依赖能力。不同环境的测试可证明其实际覆盖范围，不能用更高版本本地成功替代目标环境兼容性。
- 业务集成夹具应准备输入并经过真实业务入口产生结果。不能直接写计算结果、伪造成功状态或解释自造 SQL 来证明真实链路通过；专门的存储单元测试须明确其边界。
- 排障先区分环境、传输、数据和业务实现。性能问题对照调用次数、客户端等待与服务端耗时，再决定改动；不得仅凭等待栈推断数据库吞吐不足。
- 用例数量、结构校验和工具退出码不能替代行为覆盖。部分运行、跳过、未验证及自查必须如实标明；尊重用户明确的时间、重试预算和授权范围。

## 文档与汇报

- 概要设计先讲业务目标、现状、选择理由和实现路径；必要的领域事实、Spec 矩阵等追溯材料集中后置。保留既有字段和标题语义，旧布局仍有效。
- 开发文档面向接手的开发和运维人员：讲清业务如何运行、接口和数据如何变化、如何上线与验收。类清单、流程编号和过程日志不替代解释。
- 变更直接修订相关正文，使当前结论唯一；历史决策放变更记录。不要在末尾追加“以最新章节为准”而留下相反正文。
- 无内容的可选章节省略空表；协议必需但不适用的章节可简述“不适用”及原因。可读性依赖内容审查，不用字数、标题命中或形式表格冒充验证。
- 汇报分清代码实现、独立调试、正式流程验收和目标环境发布的状态。旧证据保留时间与范围；对当前判断有影响的独立运行应可被读者找到，不把未完成正式门禁写成从未测试。
