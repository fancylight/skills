# Codex 需求实施与交付

仅适用于 change 下的需求实施和交付；feedback 保持其独立调查与收尾规则。完整编排仍遵循 checkpoints；本文不改变 apply 的审核交接顺序。

## 选择执行方式

已有需求内的修复，在原 spec 责任明确、设计足以实施、没有未决业务或跨服务契约、没有并发写入冲突时，可以说明依据后直接实施。按需要更新原设计和 tasks，不补造 assign/report 记录，也不要求补走这些入口。跨仓数量不是判定标准；按依赖逐仓处理。

不满足条件时先澄清设计；需要完整编排时使用现有入口。子 agent 必须符合当前项目及用户授权；完整编排不自动授权委派。直接实施仍执行代码自查和适当测试，不将自查称为独立 review。用户要求独立审核而尚未取得时，交付为 UNVERIFIED。

## 设计与文件

- 领域模型、概要设计、开发文档、操作链路、task、发版记录、服务 OpenSpec 和既定测试文件全部保留。按影响维护，不机械改动未受影响的文件。
- 需求尚未完成、修复属于原责任和验收范围时，按 task 维护规则 §3.3 重开原 spec，撤销受影响的旧完成标记；实际新增范围才用 §3.4。保留旧 Git 提交，用后续提交修复，不改写提交历史。
- 一个 spec 对应一个仓库和一个 OpenSpec change；一次实施尽量一个提交，不限制后续修复提交。不能为满足提交数量而新建 spec。
- 根设计定义总体方案和跨服务契约，服务 spec 承接实现；发生偏差先修正设计或实现，不将未批准实现反写成已批准需求。开发文档按已有模板保持自包含。
- 新增文件须有需求、实现、测试或正式交付用途。临时日志、重复验证 JSON、repair-history 副本和重复总结不默认进入业务提交；不按扩展名一刀切，也不批量删除历史证据。
- 运行输出进入既有运行证据目录；正式证据保留可持续访问的位置和适用版本。复制到多处不增加证据可信度。

## 收尾责任

完整流程由根在串行 report 完成后维护并提交根文档；直接修复由当前执行者负责相同收尾。复用 report 的文档维护规则，但不伪造报告租约或调用要求租约的 report。

1. 核对本次需求、spec、实际 diff、根文档和测试证据。审核发现的文档偏差由根或直接执行者修订；审核者保持只读。
2. 显式检查暂存、未暂存、未跟踪文件及本次提交范围。仅暂存本次文件或可明确分离的 hunks；不使用无范围的 git add，不夹带其他任务的改动。归属不明即报告阻断。
3. 实施任务默认本地提交本次根文档，不自动 push；用户禁止提交时遵从并报告未提交。先用 git rev-parse --show-toplevel 确认根 .flow 的真实所属仓库，不能假定它独立建仓，也不自动 git init。
4. 用 flow-codex-check 进行最终只读校验（可先检查工作区再提交）；将简短结论写入既定实施记录后提交该记录，再核对最终提交和剩余工作区。最后的记录变化只需复核范围，不循环生成新报告。
5. 最终说明分别列出服务仓与根仓提交、验证范围和未覆盖项。既定记录保留业务提交关联，根仓 hash 仅在最终说明列出，避免自身 hash 循环。

缺少旧流程记录本身不构成失败；缺设计、代码正确性依据、适用测试或文档收尾时必须明确，不得将已提交等同完成。
