# 设计判断与反例审核

这是现有 design / verify / review 的职责，不新增阶段或审核角色。默认当前对话自查，写明 `review: self`。记录放在原设计的相关段落和原审核结论内，不为每个字段增加表格。

设计者指出会影响本次正确性的关键判断，例如标识含义、规则选择、数据范围、跨服务转换、异步完成条件。审核者先读原要求、相邻实现、表结构或代表性样本，再读作者推导。每个关键判断留下四项内容：**判断、可定位的原始依据、能够推翻判断的输入、核验结果**。

新增或改变的数据传递及查询条件，追踪实际来源、转换、存储和消费者；不重审无关旧链路。字段同类型、同值样本或相同命名不是语义等价的依据。优先复用既有实现，但必须核对它的适用范围。

以下情形拒绝通过：关键判断无依据；依据与方案冲突；反例无法区分正确与错误实现；夹具将不同概念合并而掩盖错误。不要把“文档互相一致”当作业务正确。

例如组织 ID 与项目 ID 是两个概念。分别取 101 和 202，加入其他组织或项目的干扰记录，沿请求上下文、查询条件、结果集合逐段核对。相等 ID 的夹具不能证明二者可替换。规则适用于任何被错误等同的业务概念，不按特定变量名扫描。

测试审核必须回答：**这个错误实现会不会也通过？** 修复已知缺陷，用同一断言保留缺陷版本失败和修复版本通过的证据及版本；优先复用可核实的已有构件和证据，不改写历史、不修改其他任务的工作树。其他变更按风险选择关键反例，不强制全量变异测试。

机械检查只验证记录、引用和结果齐全。字段完整不能自动获得语义 PASS；审核者负责说明预期如何独立得出、反例实际区分了什么、尚未覆盖什么。若没有实测反例，明确标为未验证。
